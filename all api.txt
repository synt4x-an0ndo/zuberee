RBAC FRONTEND INTEGRATION UPDATE — 2026-10-17
================================================================================
This section supersedes earlier statements that users/roles endpoints do not exist.
Scope: frontend changes only. No existing backend source, schema, middleware,
permission configuration, or application database data was changed.

IMPLEMENTED FRONTEND CONTRACT (inspected actual route handlers)
GET    /api/admin/users                 -> {status, users:[{id,name,email,roles:[]}]}
PATCH  /api/admin/users/:id/roles        <- {role_ids:[integer,...]} (REPLACES roles)
                                       -> {status,message,data:{id,name,email,roles}}
GET    /api/admin/roles                 -> {status,roles:[{id,name,permissions:[]}]}
POST   /api/admin/roles                 <- {name,permission_ids:[integer,...]}
                                       -> 201 {status,message,data:role}
PUT    /api/admin/roles/:id              <- {name,permission_ids:[integer,...]}
                                       -> {status,message,data:role}
DELETE /api/admin/roles/:id              -> {status,message}; 409 when assigned
GET    /api/admin/permissions           -> {status,permissions:[{id,name,...}]}
All calls reuse frontend/lib/api.js and its Authorization: Bearer token storage.

BACKEND BLOCKERS — PLEASE RESOLVE IN BACKEND, NOT IN FRONTEND
1) Application database zuberee_db has no roles, permissions, user_roles, or
   role_permissions tables (read-only information_schema/to_regclass queries).
   Authenticated GET users/roles/permissions each returned HTTP 500, for both
   ADMIN and CUSTOMER test claims. Unauthenticated GET users returned 401.
   Backend developer needs to deploy the RBAC schema/migrations, regenerate the
   Prisma client, and provision authorized roles/assignments. A separate scratch
   database was created for attempted testing, NOT applied to zuberee_db; no
   successful real-backend CRUD verification was achieved.

2) GET /api/auth/me returns only {userId,email,role}; login and account/me also
   omit effective roles/permissions. Need a fresh, server-computed permissions
   string[] on /api/auth/me for EVERY authenticated user, even those who cannot
   list users or roles. Do not use the global permission catalogue as the user's
   effective permission set, and do not infer permission from the legacy ADMIN flag.
   Frontend supports data.permissions string[] (or permission objects) if supplied.
   Current fallback derives the union of the signed-in user's assigned role
   permissions from GET users + GET roles, but ONLY when BOTH reads succeed.
   Therefore users lacking 'view users' OR 'view roles' cannot bootstrap their
   effective permissions with the current API. Frontend fails closed in that case.

3) Legacy admin endpoints (e.g. sizes) still check JWT role === ADMIN rather than
   current database role permissions. Assigning an RBAC role does not update that
   legacy enum or JWT claim. RBAC-only users may still receive 403 on those APIs;
   revocation may not take effect for those legacy APIs until token expiry.
   Backend must enforce granular authorization itself. UI hiding is not security.
